# Frontend (React + TypeScript + Vite)

## Who the user is

Compliance agents with mixed tech comfort. The benchmark from the stakeholder: "something my 73-year-old
mother could figure out." Half the team is over 50. One senior agent still prints his emails. Design for him.

## Accessibility and usability rules (mandatory)

- **Base font 18px**; body text never below 16px. Results text 20px+.
- **Click targets ≥ 44×44px.** Primary buttons are large and full-width on narrow screens.
- **One primary action per screen**, visually dominant. Secondary actions are plainly styled, never hidden.
- **No hover-only UI, no icon-only buttons, no hamburger menus, no tooltips carrying essential info.**
- **Plain verbs on buttons:** "Check label", "Check all labels", "Download results" — not "Submit", "Process", "Run".
- **Status = icon + word + color**, never color alone:
  - ✓ **Match** (green) · ⚠ **Needs review** (amber) · ✗ **Mismatch** (red) · ? **Not found on label** (grey)
- **WCAG AA contrast** minimum (4.5:1 text). Check amber especially.
- **Errors say what happened and what to do:** "This file isn't an image. Upload a JPG or PNG." Never show stack traces or HTTP codes.
- **Keyboard accessible**; visible focus rings; labelled form fields (`<label htmlFor>`), not placeholder-only.
- Drag-and-drop is a bonus; a visible "Choose file" button must always be there too.

## Pages

Top-level navigation is two large tabs, always visible: **Check one label** | **Check a batch**.

1. **SingleCheck** — image upload (with preview) + form for application fields (beverage type first, since it
   decides which fields are required). Big "Check label" button.
2. **BatchCheck** — upload one CSV + one ZIP of images. Show a validation summary before processing
   ("212 labels ready. 3 problems found:" with a list). Then a progress bar with "143 of 212 checked".
3. **Results** — one card per field: field name, *Application says*, *Label says*, status, and a one-line reason.
   Show the label image beside the results so the agent can eyeball it. Government Warning gets its own section
   with sub-checks (wording / capitals / bold). For batches: a sortable table with an overall status column,
   filter by status, click a row to open the single-result view, and "Download results (CSV)".

## Structure

```
src/
  api/client.ts         # fetch wrappers; all calls go through here
  api/schema.d.ts       # GENERATED by `npm run gen:api` (openapi-typescript) — never hand-edit
  components/           # StatusBadge, FieldResultCard, FileDrop, ProgressBar, ErrorMessage...
  pages/
  hooks/                # useVerify, useBatch (TanStack Query)
  lib/                  # formatting helpers
```

- Function components + hooks only. No class components.
- Server state through **TanStack Query**; local UI state with `useState`. No Redux.
- Types come from the generated OpenAPI schema. If a type is wrong, fix the backend Pydantic model and regenerate.
- Tailwind for styling. Define the status colors once in `tailwind.config` (`status-match`, `status-review`,
  `status-mismatch`, `status-missing`) and use those tokens everywhere.

## Batch progress

- `POST /api/batch` returns `batch_id`. Poll `GET /api/batch/{id}` every 1s with TanStack Query's
  `refetchInterval`, stop when `status` is `done` or `failed`.
- Show partial results as they arrive; don't make the agent wait for all 300.

## Performance feel

- Show a spinner with text ("Reading label…") immediately on submit. Disable the button to prevent double submits.
- Downscale images client-side to max 2000px long edge before upload (canvas) to cut upload time.

## Testing

- Vitest + React Testing Library for components. Query by role and visible text (`getByRole('button', { name: /check label/i })`) — this also enforces accessible markup.
- Every status badge, error message, and empty state has a test.
- See the `testing` skill for e2e.
